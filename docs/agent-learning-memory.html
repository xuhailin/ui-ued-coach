module · agent learning & memory

从 Agent 怎么学，到不同产品场景该怎么记。

这个模块不是技术科普，也不是仓库清单。它把 Agent 学习、记忆类型、产品定位、长对话上下文生命周期和参考实现放在同一个学习控制台里，方便快速扫视和反复查阅。

Q · 01

Agent 学习至少包括哪些能力？

7 类能力，从短期上下文适应逐步走向长期演化。

Q · 02

记忆在学习体系里处于什么位置？

记忆是关键基础设施之一，但 Agent 学习不等于记忆。

Q · 03

不同场景需要什么记忆？

助手型、陪伴型、伴侣型共享基础设施，但边界完全不同。

Q · 04

长对话什么时候压缩、召回、写入？

回答前召回，窗口快满或阶段切换时压缩，回答后抽取可保存的记忆候选。

§ 01

智能体发展史时间轴

第一部分的主线可以这样记：每一代智能体，都是在修上一代的短板。早期靠人手写规则，后来靠分布式模块协作，再后来靠数据学习、强化反馈和大模型预训练，最终形成今天“模型 + 记忆 + 规划 + 工具”的 Agent 架构。

THESIS 从写规则，到学世界，再到接工具行动。
PAIN 知识获取瓶颈、常识缺失、系统脆弱、无法处理开放环境。
NOW LLM 成为推理中枢，工具、记忆、规划和反思补齐行动闭环。
1950s-1970s
Symbolic AI

符号主义：智能等于符号推理

物理符号系统假说把智能工程化：用符号表示世界，再用逻辑和搜索推导行动。

关键词：PSSH、逻辑 AI、知识表示
1966-1970s
Rule Systems

ELIZA / MYCIN / SHRDLU：规则系统的高光

ELIZA 展示了模式匹配的“智能幻觉”；MYCIN 用知识库和推理机做医疗诊断；SHRDLU 把语言、规划、记忆和行动接进积木世界。

关键词：IF-THEN、专家系统、封闭微观世界
1980s
Limits

符号系统撞墙：常识和规模化太难

真实世界充满例外，手写规则无法覆盖常识，知识获取成本高，系统遇到规则外情况就容易失灵。

关键词：知识获取瓶颈、框架问题、脆弱性
1986
Society

心智社会：智能来自许多小模块协作

明斯基把心智看成一群简单 agent 的协作网络，而不是一个完美中央大脑。这条线后来影响了多智能体系统和模块化 Agent 架构。

关键词：Society of Mind、多模块、协作智能
1990s-2010s
Learning

联结主义和强化学习：能力开始从数据与反馈中来

神经网络解决感知和模式识别，强化学习让智能体通过环境反馈学习策略，AlphaGo 是“观察-行动-奖励-更新”的代表案例。

关键词：深度学习、强化学习、序贯决策
2018-2022
Foundation Models

大规模预训练：模型压缩世界知识

Transformer 和大规模语料预训练让模型获得通用语言理解、上下文学习和思维链推理能力，缓解了手工编码知识的瓶颈。

关键词：Transformer、预训练、涌现能力、CoT
2022-Now
LLM Agents

现代 Agent：LLM 接上记忆、规划、工具和反思

LLM 不只回答问题，而是作为认知中枢：感知用户输入，规划步骤，调用工具，观察结果，更新记忆，并通过 ReAct、Plan-and-Solve、Reflection 等范式持续迭代。

关键词：ReAct、Plan-and-Solve、Reflection、Tool Use、Memory
一句话看懂演进 规则系统擅长可控推理，但难以覆盖开放世界；学习系统擅长从数据里获得能力，但需要规划、工具和记忆才能成为能做事的 Agent。
和第 4 章的关系 第 4 章的 ReAct、Plan-and-Solve、Reflection，是现代 LLM Agent 的三种组织方式：边想边做、先计划后执行、完成后自我修正。
§ 02

Agent 范式关键词索引

先定位层级，再讨论取舍。机制层回答“能做什么”，控制流范式层回答“单个 Agent 怎么安排思考和行动”，协作范式层回答“多个 Agent 怎么分工”。框架、workflow 选型视角和组合体单独标记，避免和 ReAct 这类范式平级比较。

01 · MECHANISM 能做什么 tool use、RAG、memory、structured output 这类地基能力。
02 · CONTROL FLOW 怎么组织单体行动 ReAct、Plan-and-Execute、Reflection 这类任务执行方式。
03 · COLLABORATION 多个 Agent 怎么分工 Orchestrator-Worker、Debate、Blackboard 等协作结构。
00 · CROSS-CUTTING 横切视角 / 框架 / 组合体 Workflow vs Agent、LangGraph、Agentic RAG 这类不直接落单层。
§ 03

ReAct 的特点、局限性与调试技巧

Datawhale 第 4 章里最值得抓住的不是“ReAct 会思考”，而是它把模型输出变成了一个可执行闭环：提示词约束格式，解析器拆出 Thought / Action，工具返回 Observation，再把 Observation 写回历史，驱动下一轮决策。

01 · PROMPT 约束输出轨迹 把工具清单、用户问题、历史记录塞进模板，要求模型只按 Thought / Action 输出。
02 · PARSE 解析模型意图 从原始文本里拆出 Thought 和 Action，再把 Search[x] 或 Finish[x] 转成代码能执行的指令。
03 · ACT 执行工具动作 查工具注册表，执行 Search、Calculator、API 等真实函数；找不到工具也要生成可理解的错误 Observation。
04 · OBSERVE 回灌观察结果 把 Action 和 Observation 追加进 history，让下一轮 prompt 带着事实反馈继续推理。
FEATURES

为什么 ReAct 好用

  • 高可解释性每一步都有 Thought，可以看到为什么选这个工具、为什么继续问、为什么结束。
  • 动态纠错它不是一次性写死计划，而是根据 Observation 调整下一步，比如换搜索词、补查缺失字段。
  • 工具协同LLM 负责判断和规划，工具负责搜索、计算、查库、调用 API，能补模型知识过期和算术不稳的问题。
LIMITS

哪里容易翻车

  • 依赖模型能力推理、指令遵循或格式输出不稳，会直接导致 Action 生成错、解析失败或选错工具。
  • 串行成本高每一轮 Thought / Action 都要再次调用模型，复杂任务会累积延迟和 token 费用。
  • 提示词脆弱模板措辞、示例、工具描述稍微变化，都可能影响模型是否稳定遵循格式。
  • 可能局部最优走一步看一步缺少全局计划，容易被当前 Observation 带偏，甚至原地循环。
DEBUGGING

怎么调更稳

  • 打印完整 prompt每次调用前看最终模板、工具清单、history 是否真的符合预期。
  • 保留原始输出解析失败时先看模型原文，判断是模型没按格式，还是正则 / parser 写错。
  • 验证工具 IO检查 tool_input 是否是工具想要的格式，Observation 是否短、准、可被模型继续使用。
  • 加 few-shot 示例给一两个完整 Thought -> Action -> Observation -> Finish 样例，能明显改善格式稳定性。
  • 限制步数和温度用 max_steps 防无限循环，temperature 通常设低一点，让 Action 输出更确定。
适合用 ReAct 任务路径不确定，需要查资料、排错、调用工具、看结果后再决定下一步。
别硬上 ReAct 步骤固定、依赖清楚、可并行执行时，Plan-and-Execute、ReWOO 或 workflow 往往更省。
工程关键点 ReAct 的稳定性主要不在“会不会想”，而在 prompt 模板、输出解析、工具错误处理、history 管理和停止条件。
§ 04

低代码 Agent 平台：Coze / Dify / FastGPT / n8n

低代码平台不是新的 Agent 范式，而是把模型、工具、知识库、工作流、发布渠道和监控封装成可视化搭建环境。选型时先看任务重心：是快速做 Bot、生产级 LLM 应用、知识库问答，还是跨系统自动化。

FAST PROTOTYPE 快速原型 / 非技术用户 优先 Coze：上手快，Bot、插件、知识库、工作流和多渠道发布比较顺。
ENTERPRISE APP 企业应用 / 复杂逻辑 优先 Dify：更像 LLM 应用开发平台，适合 workflow、agent、RAG、评测和运维。
KNOWLEDGE QA 私有知识库问答 / 客服 优先 FastGPT：知识库、检索问答、客服场景和可视化流程是主线。
AUTOMATION 深度业务集成 / 自动化流程 优先 n8n：先是通用工作流自动化，再叠 AI Agent 节点和大量系统连接器。
COZE

最快把想法变成可用 Bot

定位
面向 Bot / Agent 创建的低代码平台，强调插件、知识库、工作流、发布渠道。
适合
快速原型、内容助手、运营 Bot、非技术团队验证 Agent 体验。
Agent 关联
把 tool use、RAG、workflow、角色设定和多轮对话包装成可配置 Bot。
注意
复杂企业逻辑、深度私有部署、严肃工程治理时，需要看权限、数据边界和可维护性。
DIFY

生产级 LLM 应用与 Agentic Workflow

定位
LLM 应用开发平台，覆盖聊天助手、Agent、workflow、RAG、模型管理和观测。
适合
企业级应用、复杂业务逻辑、多步骤工作流、多模态生成和团队协作。
Agent 关联
适合实现 Plan-and-Execute、Evaluator-Optimizer、Agentic RAG 等组合型流程。
注意
功能更完整，也意味着搭建前要设计数据流、节点职责、异常分支和评估指标。
FASTGPT

知识库问答和客服场景优先

定位
围绕 AI 知识库、RAG 问答、可视化工作流和应用发布的开源平台。
适合
企业私有知识库、产品文档问答、智能客服、内部知识助手。
Agent 关联
核心是 RAG + workflow，Agent 能力常用于决定查什么、怎么追问、怎么调用后续工具。
注意
知识库质量、分段、召回、重排和答案引用，比“Agent 多聪明”更决定最终效果。
N8N

把 AI 放进真实业务自动化

定位
通用工作流自动化平台，连接 API、数据库、SaaS、消息系统，并提供 AI / Agent 节点。
适合
跨系统集成、审批通知、数据同步、自动报告、运营流程和后台自动化。
Agent 关联
更偏 workflow + tool use：让模型在节点中理解、抽取、判断，再交给确定性流程执行。
注意
不要把所有节点都交给 LLM。确定性分支、权限、重试、审计和幂等要用工作流规则兜住。
平台一句话选型核心能力最像哪一层别误用
Coze先把 Agent 体验跑起来。Bot、插件、知识库、工作流、渠道发布。Agent 产品壳 + 工具 / RAG / workflow 组合。别拿它硬扛高复杂企业流程治理。
Dify把 LLM 应用做成可维护系统。Workflow、Agent、RAG、模型接入、观测与评估。应用开发平台，横跨机制层和控制流。别没设计流程就堆节点，后期会难排错。
FastGPT知识库问答和客服先看它。知识库、检索问答、引用、工作流、应用发布。RAG 平台 + 轻量 Agent workflow。别忽略知识清洗、分段和召回质量。
n8nAI 接进真实业务系统。系统连接器、触发器、流程编排、AI 节点。Workflow 自动化平台 + tool use。别让 LLM 接管确定性业务规则。
学习 Agent 时怎么放它们它们不是 ReAct、Plan-and-Execute 的同级名词，而是实现这些机制和范式的平台。
真正要比较什么比较平台时看数据接入、工具治理、流程可视化、知识库质量、发布渠道、监控评估和权限审计。
最稳妥的落地路线先用 Coze / FastGPT 验证体验，用 Dify 打磨复杂 LLM 应用，用 n8n 接业务系统和自动化链路。
§ 05

代码型 Agent 框架：AutoGen / AgentScope / CAMEL / LangGraph

Datawhale 第 6 章的重点是：当你从手写 ReAct / Reflection 走向真实系统时，框架负责把 Agent Loop、模型层、工具层、记忆层、状态管理和可观测性标准化。框架不是新范式，而是把范式工程化、可复用、可调试的脚手架。

REUSE 复用 Agent Loop ReAct、Plan-and-Solve、Reflection 都可以基于统一执行器搭出来，避免每次重写循环。
MODULAR 解耦模型 / 工具 / 记忆 模型层可替换 OpenAI、Anthropic 或本地模型；工具层负责注册执行；记忆层负责上下文策略。
STATE 标准化状态管理 长任务、多轮对话、上下文窗口、历史持久化和多智能体消息，都需要统一状态结构。
OBSERVE 可观测与调试 通过 callbacks、事件、运行轨迹和日志记录关键节点，比手动 print 更适合复杂系统。
涌现式协作 AutoGen / CAMEL 更像组织一群角色对话，让协作从消息互动里长出来。
显式流程控制 LangGraph 把流程写成状态图，节点、边、循环和条件跳转都由开发者控制。
工程化生产 AgentScope 把消息、并发、分布式和容错放到更重要的位置，适合大规模多智能体系统。
AUTOGEN

用群聊组织多角色协作

核心机制
把多智能体系统抽象成可对话的角色群聊，通过消息传递推进任务。
适合
软件开发团队模拟、评审流程、多人角色协作、人类在环监督。
优势
角色职责清晰，协作方式接近人类团队；可用 UserProxyAgent 接入人工验收。
局限
对话具有不确定性，容易偏航或循环；调试时要读长对话历史。
AGENTSCOPE

消息驱动的工程化多 Agent

核心机制
用标准消息结构、通信网络、异步并发和生命周期管理组织多智能体应用。
适合
大规模、高并发、分布式、需要容错的生产级多智能体系统。
优势
工程化强，消息驱动清晰，适合并发投票、游戏、模拟和复杂协作。
局限
学习成本更高，简单对话场景可能过度工程化；生态成熟度也要评估。
CAMEL

轻架构、重提示的角色扮演

核心机制
通过角色设定、共同任务和 inception prompting，让智能体自主展开协作对话。
适合
创作、研究、专家协作、双角色深度讨论、需要启发式输出的任务。
优势
代码负担轻，协作自然，能用少量结构激发高质量互动。
局限
高度依赖提示词；规模扩大后缺少复杂路由、状态同步和冲突仲裁。
LANGGRAPH

用状态图控制 Agent 工作流

核心机制
把状态、节点、边和条件跳转显式建成图，天然支持循环和回退。
适合
可审计工作流、Reflection 循环、可靠问答、工具链、Human-in-the-loop。
优势
可控、可预测、模块化强，每个节点都可以独立测试和替换。
局限
前期 boilerplate 较多；开放式协作不如对话框架自然。
框架设计哲学更像哪种范式优势关键词主要风险
AutoGen对话驱动协作Role-playing / Orchestrator-Worker角色复用、人类在环、群聊协作对话偏航、循环、调试历史长
AgentScope消息驱动工程化大规模 Multi-Agent / Blackboard-like messaging并发、分布式、生命周期、容错复杂度高，简单任务不划算
CAMEL角色扮演与提示驱动Role-playing / Debate-like collaboration轻量、自然协作、创造性强提示词脆弱，规模化路由不足
LangGraph显式状态图控制Workflow / Plan-and-Execute / Reflection可控、循环、条件边、可审计代码量多，涌现协作较弱
想模拟团队协作看 AutoGen；先定义角色和职责，再控制对话轮次、人类介入点和终止条件。
想做生产级多 Agent看 AgentScope；优先考虑消息结构、并发、容错、部署和生命周期管理。
想让专家角色互相启发看 CAMEL；提示词质量决定上限，适合创作、研究和深度协作。
想要可靠可控工作流看 LangGraph；适合把复杂任务拆成节点、边、循环和人类审核。
§ 06

Chat / Code 的 Prompt 进入与输出链路

不要把“用户输入的一句话”误以为就是完整 prompt。真正送进模型的是一个 prompt pack：系统 / 开发者规则、用户消息、会话历史、文件或图片、工具定义、检索结果、记忆和执行轨迹被按产品规则组装进上下文。Chat 产品更偏“回复与工具结果”，Code Agent 更偏“读仓库、改文件、跑命令、汇报验证”。

INPUT 用户这次说了什么 自然语言、截图、文件、选中文本、代码片段、任务目标。
CONTEXT PACK 系统补了什么 系统 / developer 指令、项目规则、历史消息、工具 schema、检索或记忆。
AGENT LOOP 中间怎么行动 模型可能直接回答，也可能输出 tool call、读文件、执行命令、再把结果喂回去。
OUTPUT 最后给你什么 文本、结构化 JSON、流式 token、工具结果、文件 diff、命令日志、最终报告。
OPENAI · CHAT / API

ChatGPT / Responses API

Prompt 进入用户消息 + instructions / system-level guidance + 历史对话 items。
关联上下文conversation state、previous responses、文件 / 图片、多模态输入、built-in tools、custom functions、remote MCP、可选结构化输出 schema。
中间动作Responses API 可在一次请求内执行 agentic loop：模型选择 web search、file search、code interpreter、MCP 或自定义函数。
输出形态response.output_text、typed items、function_call、function_call_output、structured JSON、streaming delta。
CLAUDE · CHAT / API

Claude Chat / Messages API

Prompt 进入system prompt + messages 数组 + 用户消息；Claude Chat 还会有产品侧系统提示。
关联上下文历史 messages、文件、图片、工具 schemas、tool descriptions、context window 管理、可选 structured outputs。
中间动作Claude 根据 tool_choice、用户请求和工具描述决定直接答还是返回 tool_use；应用执行工具后用 tool_result 继续对话。
输出形态content blocks、text、tool_use、tool_result loop、stop_reason、SSE streaming、structured output。

§ 07

Agent 学习总览

Agent 学习可以拆成 7 类能力。它们不是并列孤岛，而是从当前对话中的短期适应，逐步走向长期经验、策略和行为风格的演化。

学习能力说明典型产物适合场景阶段
上下文学习in_context在当前会话中理解任务、约束、语气、文件、工具状态。当前对话上下文、临时任务状态。所有 Agent短期
用户偏好学习preference记住用户喜欢什么、不喜欢什么、常用表达、工作习惯。用户画像、偏好标签、写作风格。助手型 陪伴型中长
任务流程学习workflow记住用户反复执行的流程、步骤、项目规则。Workflow、SOP、项目上下文。办公助手 开发助手长期
事实与关系学习facts_relations记住人物、项目、事件、组织、地点、对象之间的关系。知识图谱、实体关系、时间线。陪伴型 企业 Agent长期
经验反思学习reflection从失败、纠正、反馈中总结下次怎么做得更好。经验片段、反思规则、失败案例。高阶助手 自动化 Agent演化
行为风格学习persona学习如何表达、如何回应、边界在哪里、什么时候主动。Persona、沟通策略、主动性规则。陪伴型 伴侣型演化
自我改进学习self_improve根据长期反馈调整工具使用、提示词、策略或子 Agent 分工。Prompt 优化、技能选择、策略配置。平台型 高自主 Agent演化
Agent 学习 umbrella
上下文学习 长期记忆 工具使用改进 策略与流程优化 多 Agent 协作经验
长期记忆继续拆为 用户记忆任务记忆关系记忆情绪互动反思经验程序性记忆
§ 08

记忆深度展开

在 Agent 产品里，记忆不是简单保存聊天记录，而是让 Agent 在未来交互中更懂用户、更稳定、更少重复、更能延续关系或任务。

内容事实、偏好、事件、经验或规则。
类型偏好、事实、关系、任务、情绪、反思、禁忌等。
来源来自哪次对话、文件、用户确认、系统事件。
时间发生时间、记录时间、更新时间、失效时间。
置信度用户明确说的，还是 Agent 推断的。
可见性用户是否能看到、编辑、删除。
使用条件什么情况下应该召回，什么情况下不该用。
敏感级别是否涉及隐私、关系、身份、健康、财务等。

§ 09

人脑记忆蓝本

人脑不是一个记忆系统，而是多个并行系统：情景、语义、程序、情绪和前瞻记忆各走各的通路，召回时再融合成连贯体验。Agent 记忆也应该分系统存，统一召回。

TIME

按时长切

感觉记忆只保留亚秒级输入；短时 / 工作记忆对应当前 context window；长时记忆才进入用户、项目、关系和反思层。

ACCESS

按能否说出切

陈述性记忆可以被显式检索；非陈述性记忆更像 persona、表达风格、行为底线和工具使用肌肉记忆。

EPISODE → SEMANTIC

情景蒸馏成语义

episode 保留时间、地点、感受和当事人；图谱里的实体事实边，是多个 episode 反复发生后抽离出的语义沉淀。

AFFECT

情绪给记忆加权

陪伴型产品真正该固化的不是流水账，而是“那次用户很低落，Agent 陪了很久”这种带情绪标记的 gist。

// PROCESSES

三个过程比分类更关键

promotion / decay / rewrite
巩固 consolidation 短时不会自动进入长时。高频、重要、带强情绪或被用户确认的信息，才应该 promotion。
遗忘 forgetting 遗忘是功能，不是缺陷。decay、demotion、失效时间和主动清理让记忆系统保持可用。
重巩固 reconsolidation 每次提取都会重新写回。关系叙事需要演进，但关键锚点和来源要防止摘要漂移。
xiaoqing 四轨映射 真正的难点是融合层：四轨各自命中后，合成“此刻对用户的完整理解”。

用户轨

关于他人的语义 + 情景记忆。

图谱 / 结构化字段 + 关键 episode

未决事件轨

前瞻记忆 + Zeigarnik 效应。

图 + 闭环触发；未闭环高权重，闭环后降权

AI 自我状态轨

围绕“我是谁”的自传体记忆。

叙事承载，避免强行图谱化

关系轨

情绪加权的共享情景 gist。

叙事为主，关键时刻用图锚定
§ 10

三类场景：助手 / 陪伴 / 伴侣

这三类是产品定位，不是技术栈。它们可以共享记忆基础设施，但记忆重点、交互边界和风险完全不同。

对比项助手型陪伴型伴侣型
核心目标完成任务长期陪跑亲密关系体验
用户关系工具信任熟悉与理解情感依恋
主动性低到中中中到高
记忆粒度偏任务和规则偏用户状态和事件偏关系细节
情绪权重低中高
风险等级中中高高
§ 11

记忆实现方式

分三层看：怎么存、怎么写、怎么召回。首版不需要全部上，但选型逻辑要先想清楚。

// LONG CONTEXT

长对话：什么时候压缩、召回、写入

一轮对话的上下文生命周期
01 · 当前窗口 保留最近对话 用户刚说的约束、正在改的文件、当前任务状态，优先留在 active context。
02 · 回答前召回 查相关记忆 按项目、实体、意图、时间窗口检索，只注入当前问题需要的少量记忆。
03 · 生成回答 组装 prompt pack 系统规则 + 最近对话 + 滚动摘要 + 检索记忆 + 工具状态。
04 · 触发压缩 生成滚动摘要 当 token 接近阈值、话题切换、阶段完成、工具链很长时，把旧对话压成 summary。
05 · 回答后写入 抽取记忆候选 只从明确偏好、项目规则、重要事件、用户纠正、工具失败经验里抽取。
06 · 入库与下轮 确认后保存 普通项目事实可自动保存；身份、情绪、关系类必须让用户确认，再进入长期记忆。
Context Window 最近 N 轮原文，负责“此刻不断片”。
Rolling Summary 旧对话压缩摘要，负责“长线不丢主线”。
Memory Store 结构化长期记忆，负责“跨会话可召回”。
什么时候召回？ 回答前。先判断当前问题需要项目规则、用户偏好、近期事件还是安全边界，再检索少量相关项。
什么时候压缩？ 窗口快满、阶段结束、话题切换、工具执行链过长时。压缩的是旧上下文，不是高价值长期记忆。
什么时候写入？ 回答后或后台批处理。用户明确说“记住”、纠正 Agent、确认项目规则、工具失败复盘时才写。
什么时候不写？ 普通寒暄、一次性任务细节、不确定推断、敏感情绪和关系信息未确认时，都不要自动进长期记忆。
方式说明优点缺点适合
原始聊天记录保存完整对话，需要时检索或摘要。实现简单，证据完整。噪声大、成本高、隐私压力大。审计、回放、轻量 MVP。
摘要记忆将对话压缩成阶段摘要。成本低，读起来清楚。容易丢细节和来源。陪伴日志、阶段复盘。
结构化字段用 profile、preference、project 等字段保存。可控、可编辑、好展示。灵活性较弱。首版记忆面板
向量记忆用 embedding 检索相关片段。语义召回方便。可能召回错、难解释。通用助手、知识问答。
关键词 / BM25基于关键词检索。可解释、成本低。语义能力弱。名称、项目、明确事实。
混合检索向量 + 关键词 + 重排。召回更稳。系统复杂度更高。中长期产品。
知识图谱建实体、关系、时间与来源。适合关系和时间推理。建模和维护成本高。长期陪伴、企业知识。
时间线记忆按日期、事件、阶段组织。适合回顾和陪伴感。不适合复杂语义检索。陪伴型、成长型。
反思 / 经验库存失败、纠正和策略。能让 Agent 越用越顺。需要质量控制。高阶助手。
用户显式保存用户说“记住这个”或手动添加。适合高价值偏好和敏感信息。
Agent 自动抽取每轮对话后抽取可能有用的记忆。适合普通偏好、项目事实。
后台批处理整理定时总结、去重、合并、过期。适合长期陪伴和知识库。
工具事件写入工具执行成功或失败后记录经验。适合工作流 Agent。
用户确认后写入Agent 提议保存，用户点确认。适合情绪、身份、关系类记忆。
首版建议：核心偏好使用显式保存 + 提议保存；项目记忆可自动抽取但必须可编辑；情绪和关系类记忆必须确认后写入；反思记忆标注“推断 / 总结”。
固定注入每次都把少量核心记忆放进系统上下文。
语义搜索根据用户当前问题检索相关记忆。
时间窗口召回最近一段时间事件，适合陪伴感和阶段复盘。
实体关系查询根据人、项目、对象查询关系，适合图谱型记忆。
规则触发特定任务或页面触发特定记忆。
Agent 自主搜索Agent 判断何时查记忆，适合高级助手。
首版不要让所有记忆默认进入上下文。固定注入少量核心偏好，项目 / 事件记忆用语义搜索 + 时间窗口。
